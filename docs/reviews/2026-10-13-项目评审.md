## 0. 一句话结论

**这是一个工程纪律远超同体量个人项目的仓库——文档体系、契约先行、DIP 双实现、oracle 验证、隐私与 SSRF 纵深防御都达到了可对外讲的标准。** 但它当前处在「内部质量优秀、对外交付未闭环」的临界点：**LICENSE 缺失 + 权限分离 P0 未收尾 + 硬编码默认密钥 + 无对外接入指南/未发 npm**，使它尚不能作为「可开源项目」交付给陌生人。建议把剩余精力集中在**发布级收口**，而非继续扩功能面（M8-M12）。

## 2. 亮点（值得保留并推广）

1. **文档即工程资产**。五层文档各司其职（什么/契约/拓扑/为什么/进度），且带**状态标注**（✅ 已实现验证 / 🚧 规划 / ✂️ 明确不做 / ⚠️ 有边界）。`PRD.md:318` 的「变更纪律：先改 PRD 再动代码」与 `ARCHITECTURE.md:126` 的「修复与复审 SOP 五步」把流程写成了可执行约束，不是口号。
2. **契约先行真正落地**。`packages/protocol` 的 zod schema 是单一事实来源，TS 类型全部由 `z.infer` 推导（`schema.ts:245-258`），SDK 端 `import type` 摇树、服务端运行时校验共用一套。`PROTOCOL_VERSION` 加性演进纪律清晰。
3. **DIP 双实现贯穿存储**。`IEventQueue / IEventStorage / IRateLimiter / IProjectStore / IIssueStore` 接口化，Memory 形态永久保留为零依赖起步（`ARCHITECTURE.md:96`），CH/PG 只是实现替换。这使 CI/e2e 不依赖 docker 也能跑全链路。
4. **可靠性设计的取舍是清醒的**。`batchSender.ts` 的通道状态机（active/leaving）、beacon 按 **UTF-8 字节**精确装箱（`batchSender.ts:230-262`，修复了旧实现 UTF-16 判长低估 CJK 的 bug）、重试耗尽才落 IndexedDB 且 **2xx 确认后才删**（`replay()`）、4xx 不重试、keepalive 64KB 硬限主动放弃——每条都有注释说明「为什么这样取舍」。
5. **隐私与安全的纵深**。出口 `maskDeep` + 服务端 ingest 二次脱敏（**先脱敏后指纹**，保证跨版本分组稳定）、SSRF 双道（字面值 BlockList + 连接时 DNS 复核 + 重定向逐跳，`webhook-url.ts` 与 `alert-engine.ts:43-71`）、有界解析（gzip 解压输出 2MB 上限、fetch 响应流式有界读 4096B）。
6. **Skill 是活的**。`.zcode/skills/code-review-expert/SKILL.md:43-53` 的「项目附加纪律」列的是**本项目真实踩过的坑**（异步 unhandled rejection 判红两次、Nest DI 显式 token 连续踩三次、录屏空壳/TraceId 死代码的「声明与实现一致」红线）。这把「审查清单」从通用模板升级成了组织记忆。

## 3. 阻塞问题（P0 — 发布前必须闭环）

### [P0-1] LICENSE 文件缺失，但 README/package.json/PUBLISH 都声明 MIT

- **修复**：新增标准 MIT `LICENSE`（版权行填实际持有人），`README` 链接即生效。
- **验收**：仓库根存在 `LICENSE`；`README.md` 链接可达；npm 打包 `files` 含 LICENSE（或随 README 自动带出）。

### [P0-2] 服务端权限分离（项目自评 P0）仍在途，未收尾

- **位置**：`docs/tasks/CURRENT.md:40`（`[ ] P3 权限分离` 未勾）｜`docs/tasks/CURRENT.md:52-58`（§3.2 验收条件）
- **现状**：`auth/management.guard.ts` 已落地双通道（项目密钥 + 会话 cookie），`query.controller.ts` 已改为 `ManagementGuard` + `req.apikey` 隔离——**方向正确且是本次未提交 diff 的主体**。但：
  - `CURRENT` 尚未勾销，验收条件（「公开 key 无法访问查询/告警/SourceMap API（401/403 用例锁定）；管理凭证全功能回归」）未见闭环记录；
  - dashboard 登录链路（`LoginView` + `session-check`）与 `server.e2e.test.ts` 的权限用例是**同步改动**，需确认 401/403 负向用例已进回归。
- **风险**：这是 PRD 明确的「公网部署与 npm 发布前置」，也是全项目**唯一剩下的发布级安全闸门**。
- **修复**：补齐负向验收用例并勾销 P3；确认 `/api/**` 全端点（含 `/api/alerts/*`、`/api/sourcemaps`）都在 Guard 覆盖下。
- **验收**：持公开 `public_key` 调 `/api/overview` `/api/alerts` `POST /api/sourcemaps` 全部 401/403；持会话 cookie / secret key 全功能 200；用例进 CI。

## 4. 建议修复（P1）

### [P1-1] 默认管理员凭证与会话密钥可被带到生产（硬编码弱密钥）

- **位置**：`apps/server/src/config.ts:26-28`
  ```ts
  adminEmail:    z.string().email().default('admin@demo.local'),
  adminPassword: z.string().min(1).default('demo-password'),
  sessionSecret: z.string().min(1).default('dev-insecure-session-secret'),
  ```
- **问题**：zod `.default()` 使应用在**任何环境都能带默认值启动**。若部署方忘记覆盖 `ADMIN_SESSION_SECRET`，会话令牌（`session.ts` 的 HMAC-SHA256）用**公开已知的密钥**签名 → 任何人可伪造管理会话；`demo-password` 同理。注释写了「生产必须覆盖」，但**「文档声明的边界」不等于「安全的默认」**——这恰好违反项目自己的「配置项 = 承诺 / fail-fast」纪律（`ARCHITECTURE.md:124` 启动期校验失败应直接失败）。
- **修复**：生产环境（`NODE_ENV=production`）下，若三个值仍是默认值 → **启动即抛错**（fail-fast），而非静默使用；或强制 `ADMIN_SESSION_SECRET` 无默认值、必填。
- **验收**：`NODE_ENV=production` 且未设 env 时进程启动失败并给出明确错误；设 env 后正常启动。

### [P1-2] `/report/batch` CORS 反射任意 Origin 且带 Credentials

- **位置**：`apps/server/src/report/report.controller.ts:34-35`
  ```ts
  res.setHeader('Access-Control-Allow-Origin', origin || '*')
  res.setHeader('Access-Control-Allow-Credentials', 'true')
  ```
- **问题**：把请求 `Origin` 原样回写为允许源，并开启 `Allow-Credentials`。这是安全清单里的典型误配（「Overly permissive CORS：`*` + credentials」）。虽然 `/report/batch` 的鉴权在**信封体 apikey**（公开标识，非 cookie），实际越权面有限，但：① 该响应头**对 400/403 错误响应同样生效**，跨源页面可读取错误细节；② 与 `Allow-Credentials` 组合违背最小权限原则；③ 若未来接入 cookie 鉴权即成高危。
- **修复**：该端点不用 cookie → **移除 `Allow-Credentials`**；如需限制来源，用 `PROJECTS_JSON` 中登记的回调域做白名单，未命中回退 `*` 但不带 credentials。
- **验收**：跨源探测脚本确认响应不含 `Allow-Credentials: true`；带 `Origin: https://evil.example` 时错误响应不可被跨源读取。

### [P1-3] 无界内存集合（登录失败表 / 告警冷却表）

- **位置**：`apps/server/src/auth/auth.controller.ts:43`（`fails` Map，按 email 增长，永不回收）｜`apps/server/src/alert/alert-engine.ts:81`（`cooldown` Map，按 ruleId 增长）
- **问题**：代码质量清单「Unbounded collections」。攻击者用大量不同 email 撞库即可让 `fails` 表无界增长（内存 DoS）；冷却表随规则数/历史增长。
- **修复**：`fails` 加容量上限或过期清扫（lock 过期即删条目）；`cooldown` 随规则删除清理。
- **验收**：注入 10 万不同 email 失败后 `fails.size` 有界；规则删除后 `cooldown` 无残留。

### [P1-4] Memory 存储错误去重误抑制（项目已知，仍开放）

- **位置**：`apps/server/src/storage/memory.storage.ts:14`（永久 Set 按 `apikey+errorId` 去重）
- **问题**：把 SDK 允许的第二次同类错误与跨会话同类错误都当重试丢弃，且 Set 不随事件淘汰。**Memory 形态是零依赖起步形态 + 全链路 e2e 的运行形态**，此缺陷影响默认体验。项目已挂账并入 M7.5 P4（需先在 SPEC 定义稳定事件 ID 与窗口）。
- **修复**：按 CURRENT §3.3 的验收条件实现「稳定事件 ID + 去重窗口 + 有界状态」。
- **验收**：两次真实发生及跨会话同类错误都计数；同一事件重放只计一次；>5 万事件后去重状态有界。

## 5. 可选优化（P2）

### [P2-1] 死代码 / 未消费配置与「声明=承诺」红线冲突

- **位置**：`docs/tasks/CURRENT.md:84`（P2 挂账清单）
- **问题**：`silentHashchange` 零消费、`core/logger.ts` 整文件死代码、utils 15+ 死导出、两份 `ERROR_TYPE_RE` 正则零引用、shared constants 与 session 字面量两套并存、信封 `referrer/viewport` 未接线、`beaconPost/xhrPost` 生产零调用。这些正是本项目 skill 第一条红线「**配置项 = 承诺；新增配置必须有消费点**」所指的情形——**规则已立，但存量未清**。
- **建议**：借一次「清零批次」集中删除（`removal-plan.md` 模板已就绪，正好用它填表），并在 CI 加 `knip`/`ts-prune` 类死码检测防回流。

### [P2-2] 看板前端与定稿设计之间存在「从零重建」的落差

- **位置**：`apps/dashboard/src`（892 行、5 个浅色视图、**零测试**）vs `apps/dashboard/design/`（21 页暗色高保真原型，2400 行）
- **问题**：`CURRENT.md:50` 已诚实量化——P5+M8+M9 前端 ≈ 设计系统 + 应用壳 + 20 页全新构建。这是**剩余工作量最大、且无测试护栏**的模块。
- **建议**：按 CURRENT 建议拆批（P5a 设计系统 token + 壳 + 登录 → P5b 页面迁移）；**为看板补最小测试**（至少登录/权限跳转/详情下钻的冒烟），否则前端成为唯一无门禁的交付面。

### [P2-3] 产品交付链未闭环：npm 未发、无对外接入指南

- **位置**：`docs/tasks/CURRENT.md:100`｜`PUBLISH.md:78-88`
- **问题**：B 档验收标准是「陌生人 15 分钟接入成功」，但 npm 注册被反滥用拦截、对外接入指南「待产品落地后补」。**结果是：能力已建成，却无法被目标用户验证。** 这比任何功能缺口都更影响「可开源项目」的成色。
- **建议**：① 备一条发布 fallback（GitHub Packages / 自托管 registry），别让单一 npm 账号成为单点；② 优先写一页「15 分钟接入指南」（README 快速开始已具雏形，抽出为独立 guide 即可）；③ 找一个真实外部用户做接入验收。

### [P2-4] 范围与路线图对单人偏乐观

- **位置**：`docs/PRD.md:296-314`（M8-M12 路线图）
- **问题**：M8(3周)+M9(3周)+M10(2周)+M11(3周)+M12(2周) = **13 周**，且 M8/M9 是「看板横切 + 埋点分析」这类重前端重后端工程。同时 SDK 侧还有 M8 前小切片（captureException/错误过滤/consent）与 P2 挂账。对单人维护者，这是**能力清单而非交付承诺**的合理自我认知，但对外叙事若按路线图承诺会失真。
- **建议**：保持 PRD 的「三档演进」诚实框架（A 档 Web 核心 → B 档开源 → C 档 SaaS），把 M8-M12 明确标注为「候选路线」而非「计划」；对外只承诺 A 档已验收范围。

## 6. Skill 标准评审（`.zcode/skills/code-review-expert`）

### 6.1 做得好的

- **结构完整**：触发 → 范围（默认 `git diff HEAD`）→ 流程（获取全貌 → 理解意图 → 四清单 → 项目附加 → 分级输出）→ 输出模板（P0/P1/P2 + 亮点）→ 审查员自律红线。
- **反误报纪律**：`SKILL.md:36`「每条嫌疑都必须到源码核实后才能列为问题（禁止凭 diff 片段臆断）」+ `:81`「不确定标『待确认』，误报比漏报更消耗信任」——这是审查类 skill 最稀缺的克制。
- **项目附加必查项**（`:43-53`）把真实事故转成检查项，含「修复深度复审：不认可『现象消失即修好』」「字面值过滤 ≠ SSRF 防护（`localhost.` 尾点实证可绕过）」——含金量极高。
- **与项目 SOP 打通**：要求每条问题带「验收条件」，直接对接 `ARCHITECTURE.md §7.3` 的修复五步。

### 6.2 建议补强

1. **缺前端/UI 专项清单**。看板是项目一等交付面，但四清单全是后端/通用视角。建议加 `frontend-checklist.md`：React Hooks 规则（**本次未提交的 `App.tsx` 改动恰好在修一个 Rules-of-Hooks 违例——把 `useEffect` 从条件 return 之后移到之前**）、effect 依赖完整性、列表 key、无障碍与错误边界。这个真实 diff 说明该类问题是现实存在的。
2. **缺「评审预算 / 风险分级」指引**。当 diff 很大（如本次 P3 跨 5 文件）时，skill 未指导如何按风险切分优先级（安全 > 数据正确性 > 可维护性），容易均摊注意力。
3. **缺供应链与依赖的可执行步骤**。`security-checklist.md` 提到「Unpinned dependencies / dependency confusion」，但没有给出可执行命令（如 `pnpm audit`、锁文件校验、私有 scope 占位）。
4. **`removal-plan.md` 仍是空模板**。它存在但从未被填写——建议第一次死代码清零批次就用它产出实例，把模板变成范例。
5. **缺「验证必须看退出码」的通用化**。项目附加项里有「验证纪律：检查退出码，禁止用管道 grep 输出行数代替」，但这条对本项目通用且代价极低，建议提升到主流程第 4 步（输出报告前）作为通用要求。

## 7. 结论与建议优先级

| 优先级 | 事项 | 类型 | 预估 |
|---|---|---|---|
| P0 | 补 `LICENSE` 文件 | 交付阻塞 | 5 分钟 |
| P0 | 收尾 P3 权限分离 + 401/403 负向用例进 CI | 安全 | 0.5-1 天 |
| P1 | 生产环境默认密钥 fail-fast | 安全 | 0.5 天 |
| P1 | `/report/batch` 去掉 `Allow-Credentials` | 安全 | 10 分钟 |
| P1 | 无界 Map 加界；Memory 去重按 P4 设计修 | 健壮性 | 1-2 天 |
| P2 | 死代码清零批次（用 removal-plan 填表） | 可维护性 | 1 天 |
| P2 | 写对外 15 分钟接入指南 + 发布 fallback | 产品交付 | 1-2 天 |
| P2 | 看板补最小测试护栏 + 按 P5a/P5b 拆批 | 质量 | 随 P5 |

**总体判断**：`可合并`（内部质量层面）——但对外发布前**必须**先清 P0。项目最该做的不是加 M8-M12 的新功能，而是**把已经建成的 A 档能力「发出去、被陌生人验证」**。当前的最大风险不在技术，而在「完美主义式地继续建，却迟迟不交付」。
